What gets created

  • Two targets per service, sixteen in total: 99.9% of requests succeed, and 99% finish within 500 ms. Both judged over the last 30 days of traffic.
  • A target of 100% is rejected with a 400. It leaves no room to fail at all, so the very first failed request out of payment would put it permanently behind with no way to recover.
  • The speed target must be one of 100/250/500/1000/2000 ms, because those are the only cut-offs the services actually record timings against (their histogram buckets). Ask for 400 ms and the query returns nothing at all rather than an error.

What the injection does

  • 35% errors and +600 ms into ledger-service, applied through that service's own chaos endpoint.
  • ledger-service is the deepest node in the order path and calls nothing, so everything that fails above it is a consequence, not a second cause.
  • The browse path is deliberately left alone. It is the control: if it breaches too, correlation is grouping by time rather than by dependency.

The thresholds behind it

  • A breach needs both windows over the line: 2 m long and 1 m short in this profile, at 14.4× for CRITICAL. The long window proves it is sustained, the short one proves it is still happening.
  • Correlation walks only the subgraph induced by breaching services. Over the full graph all eight are permanently one component and every failure would collapse into one incident.
  • The correlation key is frozen at creation. The origin is recomputed for display, but an incident is never re-keyed.

How it closes itself

  • Reset clears chaos on all eight services. It does not touch incidents; those are closed by the platform or not at all.
  • Auto-resolve needs 4 minutes with no breach on any member, swept every 15 s in this profile. Twice the correlation window, so a cascade drawing breath is not mistaken for a recovery.
  • Nothing is acknowledged or closed by hand. The full timeline is kept for a postmortem.

This draft was written without a language model. The drafter is a seam, not a hard-wired dependency: point LLM_BASE_URL and LLM_API_KEY at any OpenAI-compatible provider and the same timeline is sent to a model instead, which returns the same four sections written as narrative. Nothing else in the pipeline changes. The deterministic path stays as the fallback, so a provider outage, a rate limit or an expired key degrades the wording and never the detection — and the demo needs no signup. Richer analysis — correlating deploys, config changes and log excerpts — plugs in at this same seam as the inputs become available.

Reference — how it works, and why these choices
1
The services
Eight of them, calling each other synchronously, so a failure at the bottom reaches the top.
— 2
Prometheus
Scrapes every 15s. Recording rules pre-compute the burn rate for every service, so the query count depends on the number of windows, not the number of services.
— 3
Evaluator
Every 15s asks: enough data to judge? is the burn rate over the line in both the long and short window? If it cannot see, it says so; it never guesses "broken".
— 4
Kafka
Breach events keyed by service name, with deterministic ids so a redelivery is recognisable. Detection never waits on correlation.
— 5
Correlator
Takes the dependency graph, throws away every service that is not currently breaching, and groups what remains. Connected breaches become one incident; disconnected ones stay separate.
— 6
Root cause drafter
A second consumer, on its own thread. Builds the timeline, sends it to a model, and stores the draft on the incident, or writes the deterministic summary when there is no model to reach. Detection never waits for it.
—
The decisions that are not obvious from the diagram, and what each one is defending against. Most of these are bugs that were found and fixed rather than principles chosen up front.
1
The correlation key is the origin, not the set of affected services
Hashing the member set looks right and quietly breaks the demo: the set grows as the cascade spreads, so every new breach produces a different key and its own incident: four services, four incidents, exactly the storm this exists to collapse. The origin breaches first and stays first, so all four resolve to one key. It is frozen at creation: recomputed for display, never re-keyed.
2
The Redis dedupe mark is set after the commit, never before
Marking first is faster and silently loses events: mark, commit fails, Kafka redelivers, the mark is found, the consumer logs DEBUG and returns, and the breach is gone with no incident, no dead letter, and no counter to notice it by. Marking afterwards leaves only a duplicate-delivery window, which the partial unique index absorbs.
3
Three dedupe layers, ordered rather than redundant
A deterministic v3 event id makes a redelivery recognisable; the Redis key skips the common case cheaply; the partial unique index on correlation_key WHERE state <> 'RESOLVED' catches the commit-to-mark race and concurrent consumers. Verified with 50 threads on one key, and with 10,000 replayed duplicates.
4
Correlation walks the subgraph induced by breaching services only
Over the full static graph all eight are permanently one component, so any breach anywhere would collapse into a single incident and correlation would be doing no work at all. Inducing on the breached set is what makes Break both paths produce two incidents instead of one.
5
Burn rate is precomputed in Prometheus
A cycle is about six instant queries however many services there are, because the recording rules aggregate by (service) and one query returns every service as a vector. Querying per SLO per window would be 4000 queries a cycle at 1000 services, and Prometheus rather than Sentinel would be the story.
6
The LLM is optional, and the fallback is a feature
Required-and-degraded would mean the observability platform depends on a third party's uptime in order to explain outages. With no key the deterministic drafter is wired at startup; with a key and a failing provider, retry and a circuit breaker run and then the same summary is written. Either way the incident is explained, and the response says which wrote it.
7
The RCA is written by a targeted UPDATE, not through the entity
Rewriting the whole row dragged the draft into the @Version contention that protects the affected-services set. Acknowledging an incident while the drafter finished threw a stale-object exception and returned 500, over columns that cannot conflict. The conditional update also makes draft-once atomic.
8
An LLM failure does not dead-letter
Retries are exhausted, the deterministic summary is written, the message is acked. Dead-lettering would leave the incident with no root cause at all, which is strictly worse than one with a plain timeline. The DLT is for messages that need a human.
9
Sharding was built on day one and is still switched off
ShardAssignment is ten lines and makes horizontal scaling a config change. Naive replicas would each evaluate every SLO and triple-count the burn rate. It runs at 0/1 because the measured ceiling has not been reached, and naming your own ceiling is the honest version of this answer.
10
The demo runs compressed SLO windows
Production defaults are 1h/6h/3d; this profile uses 2m/1m. On production windows the first CRITICAL lands around three minutes in, and on a freshly started stack rate() has seconds of history so the burn rate spikes for the wrong reason, so the demo would work cold and degrade as it ran. Declared here rather than found later.
Prometheus has no dashboards — it is a query console, and it opens blank on purpose. These open it with the query already run. Everything on the two Grafana dashboards is one of these underneath.
Check the first one before you trust any of the others. If request rate is flat at zero the baseline load generator has stopped, rate() has nothing to average, and every burn rate on this page and both dashboards is meaningless rather than healthy.

Running the demo profile: SLO windows are compressed to 2m/1m so a cascade is visible in two minutes. Production defaults are 1h/6h/3d; see Why These Choices under Reference.
